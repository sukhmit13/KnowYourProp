# KYP — Step 10: New Construction → top-level section

### This step is a **consolidation** first and a redesign second. Read §1 before writing any CSS.

There are currently **four** places on the page that answer "is anything being built near this
property?", and three of them compute it independently, from the same Socrata dataset, with
different windows, geographies and filters. Two of the three are wrong. Styling one of them
without deleting the others just makes the disagreement prettier.

🔴 **Scope:** change only what this document specifies. Do not restyle, refactor, or "make
consistent" any other section. Do not touch Permits & Violations (section 03) — that section is
about permits **on this parcel**; this one is about permits **near** it. They are different
questions and must stay separate sections.

## 1. Consolidation — do this first

### 1A. Delete Surface C, do not fix it

`RunDetail.tsx:16039–16048` renders `proximityData.newConstruction.countInHalfMilePast5Years`
as **"N in ½ mile · Past 5 years"**.

Look at `server/pinResolver.ts:1684`:

```ts
const url = `${PROXIMITY_API_BASE}?pin10=${pin10}&$order=year DESC&$limit=5`;
```

One row per assessment year, capped at five. Each row's `nearest_new_construction_pin10` is
**the single nearest new-construction parcel in that year**. The code then counts distinct
PINs among those ≤5 rows and labels the result as a count of new construction in a half mile.

It is structurally incapable of exceeding **5**, and it is not measuring buildings — it is
measuring *how many of the last five assessment years had their nearest new build inside a half
mile*. A block with sixty new buildings and a block with three both render the same number.

Delete the tile. Leave the rest of `fetchProximityData` alone — foreclosures and vacant land
use different fields on the same response and are out of scope. Remove only the
`newConstruction` block from the returned object and its render site.

### 1B. Delete Surface B, serve from Surface A's cache

`server/upcomingDevelopments.ts:227` fetches `ydr8-5enu` for `PERMIT - NEW CONSTRUCTION` over a
**6-month** window (`:223`), with **no accessory-structure filter** and **no dedup**. Its
results render as `stage === 1` items at `RunDetail.tsx:19836–19895`.

`server/newConstruction.ts` already caches a **citywide 3-year** array of the same permit type,
already excludes accessory structures (`:174–199`), already dedups. Surface B's result set is a
strict subset of it, minus the two filters — which means B shows garages and duplicate rows
that A correctly hides, side by side, on the same page.

- Remove the stage-1 fetch from `upcomingDevelopments.ts`.
- `upcomingDevelopments` keeps **only** its stage-2 items (the Block Club / news-derived
  proposed developments). That section is now purely "things announced but not yet permitted,"
  which is a real and distinct thing.
- Delete the stage-1 `<Collapsible>` at `:19836–19895`.

### 1C. One client for `ydr8-5enu`

Extract one:

Every caller — `newConstruction.ts`, `upcomingDevelopments.ts`, `Compare.tsx`'s backend, and the

## 2. Server — `server/newConstruction.ts`

### 2A. The subject is 1 mile; community area is a benchmark

Return one object, not three scopes:

```ts
export interface NewConstructionResponse {
  // subject — within 1 mile of the parcel
  nearby: {
    permits: NewConstructionPermit[];   // all of them, nearest first
    totalCount: number;
    byCategory: Record<PermitCategory, { count: number; medianCost: number }>;
    byYear: Record<string, number>;     // total only — no category split
    last12: number;                     // issued in the trailing 12 months
    prior12: number;                    // issued in months 13–24
    changePct: number | null;           // null when prior12 === 0
    activeCount: number;                // issued within 18 months
    nearestActiveMiles: number | null;
    nearestActiveAddress: string | null;
    permittedUnits: number;             // Σ units across multifamily permits
    permittedUnitBuildings: number;
    largestUnitCount: number;
  };
  // benchmark only — one number, never its own view
  communityAreaName: string;
  communityAreaTotal: number;           // same window, same filters
  periodStart: string; periodEnd: string;
  latestIssueDate: string;
}
```

### 2B. Delete the ZIP scope entirely

`:440` filters `p.contact_1_zipcode === zipCode`. That is the **permit applicant's mailing
ZIP**, not the property's — a developer headquartered in Naperville drops out of the count for
the ZIP they are building in. The field cannot answer the question, and community area already
covers "the neighbourhood." Remove `zipCode`, `zip`, and the toggle option.

### 2C. Median, not mean

`computeStats` returns `avgCost` and a `skewed` flag. Reported permit cost is right-skewed by
construction — one tower sits in the same column as twenty two-flats. The code detects the skew
and prints the mean anyway with `· skewed` appended.

Return **`medianCost`** and delete `avgCost` and `skewed`. Label it "median" in the UI.

While you are here: two different averages for the same category are currently visible at once
— the community tiles divide total cost by **all** permits, the nearby tiles divide by
**priced** permits only. Median resolves this, but state the denominator in the source line:
*"Median of permits reporting a cost; N of M reported none."*

### 2D. One trend algorithm

Two disagree on screen today: server `trendDirection` (trailing 12 vs prior 12, ±10%) drives
the collapsed badge, client `trendWord` (full calendar years + monotonicity) drives the
expanded chip. A section can show "Trending Up" collapsed and "Stable" expanded.

Keep **trailing 12 vs prior 12**, on the nearby scope. Delete `trendWord` from `RunDetail.tsx`.
Rationale: calendar-year monotonicity needs three full years to say anything and goes silent
in Q1; the trailing window always has an answer and matches what "up 83%" means to a reader.

## 6. 🔒 Colour — encodes the CLAIM, never the category

New construction near a property is genuinely ambiguous, and the section must not pretend
otherwise. Three numbers, three different claims.

| Block | Number | Colour | Because |
|---|---|---|---|
| 1 | builds within 1 mile | **indigo** | a count with no benchmark makes no claim; the community-area figure sits in its breakdown rows as context, not as a verdict |
| 2 | trend `+N%` | **green** if `changePct ≥ +10`, **indigo** if within ±10, **indigo** if falling | capital arriving lifts land value for every owner type. Cooling construction is not a defect — never orange, never red |
| 3 | permitted units | **gated — see §7** | |

**Nothing in this section is ever red.** Red requires the record to be authoritative on the
question, or the fact to describe something unlawful or unfinanceable (§11). A permit for a
building near you is neither. There is no count of nearby construction that makes a property
defective.

⚠️ **Every filled block's label must state the claim in words, not the category.** Green
`#2f7d3f` and orange `#e07a2e` sit 25.6 ΔE apart to normal vision but only **7.9 (protan) /
5.9 (tritan)** — a colour-blind reader sees blocks 2 and 3 as the same colour. The label is the
only thing that separates them.

```
✗  NEW UNITS PERMITTED WITHIN 1 MI
✓  NEW UNITS COMING — COMPETING SUPPLY
```

## 7. 🔒 Gated logic

Compute these; do not tell the user to check anything manually.

1. **The unit-supply flag (block 3).** Orange **only when all of:** the subject property has
   `units >= 5` (assessor class or listing unit count), **and** `permittedUnits >= 25`, **and**
   `permittedUnits >= 2 × subjectUnits`. Otherwise **indigo**, label
   `NEW UNITS COMING — NEARBY SUPPLY`, no callout. A house buyer and an owner-user get no claim
   from the same 340 units; a 12-unit landlord does. This is the *"a million-dollar house does
   not mean you have cash to fix the toilet"* rule: land value up ≠ cashflow up.

2. **Render the `.kyp-disc` callout only when the flag fires**, and have it name the gate in
   plain language ("this property is a 12-unit rental"). A dormant rule renders nothing.

3. **`changePct = null` when `prior12 === 0`.** A rise from zero is not a percentage. Render
   "first new construction within a mile in two years" and colour the block **indigo** — one
   permit after a dry spell is not a trend.

4. **Suppress the trend block entirely when `last12 + prior12 < 4`.** Percentages on tiny
   counts are noise: 2 → 4 is "up 100%" and means nothing. Show the raw counts instead.

5. **`activeCount`** = issued within 18 months. This is a *proxy* for "under construction," and
   the status strip must say so — "likely still building," never "under construction."

6. **Nearest-active proximity.** If `nearestActiveMiles < 0.1`, add a `.kyp-loc` callout:
   construction inside two blocks is a real near-term disruption claim. Between 0.1 and 1 mile
   it is context and stays in the status strip. **Distance alone never turns a block orange** —
   only the callout appears.

7. **YTD pace is a projection and must be labelled one.** Keep the existing straight-line
   calculation and the "spring and summer are peak filing season" caveat. Never let the
   projected figure enter the trend calculation.

8. **Benchmark honesty.** `communityAreaTotal` is a raw count over a much larger area — it is
   **not** normalised and must never be compared to the 1-mile figure as a ratio. Print it as
   context only: "West Town: 218 over the same window."

9. **Citywide fallback must not silently lie.** Today, when no community-area match is found,
   the code falls back to citywide numbers while the banner says "No neighborhood-specific
   results found" — and the summary bullet above it still reads "15 new construction permits in
   Beverly." If the community-area lookup fails, **omit the benchmark row**. Do not substitute
   a different geography under the same label.

10. **Units are the applicant's figure at filing.** They are not re-verified at completion and
    projects get value-engineered down. Say so in `.kyp-src`. Never present `permittedUnits` as
    delivered supply.
