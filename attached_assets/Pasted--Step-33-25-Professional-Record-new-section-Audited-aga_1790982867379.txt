## What the section is

Everyone on the public record who has worked on this address, grouped by profession, most recent
first. The reader is a buyer doing diligence: *who already knows this building?*

It is the property-scoped mirror of Discovery, which already ranks the same professions citywide
(`Discovery.tsx:670` — `gc-rankings`, `architect-rankings`, `expeditor-rankings`,
`lender-rankings`, `commercial-lender-rankings`, plus tax-appeal attorneys at
`routes.ts:8226`). Nothing here is a new concept; it is an existing directory, scoped to one
parcel.

### The one rule that governs the whole section

**No verdict colors anywhere in §25.** Every block is `.ind` or `.slate`; every chip is a
`.kyp-pill ind` or a `.kyp-tag rec`. Nothing in this section has an outside authority classifying
it with a polarity:

- A contractor with 212 permits is not thereby good.
- A granted variation is good for whoever applied — usually the previous owner. Whether it is good
  for this reader depends on what they intend to do with the parcel, so polarity depends on
  intended use → slate.
- ARDC verification looks like an authority but has no polarity: `not_attorney` only means the
  representative was not a lawyer, which is often the owner appearing for themselves.

If a later change introduces `.grn` / `.orange` / `.red` into §25, it is wrong.

### Outcomes, and the line this section does not cross

The section shows **the outcome of a matter**, attached to the matter, in the words of the body
that decided it: `GRANTED`, `DENIED`, `2 OF 3 DECREASED`.

It must never show **a success rate for a person**. Not "1 for 1", not a win percentage, not a
rank. Three reasons, and all three hold:

1. The outcome belongs to the *application*, not to the lawyer. Attributing it to them is our
   inference, not the record's.
2. On a single property n is almost always 1–3. Any rate computed from that is noise.
3. It would publish a performance statistic about a named individual — a "0%" derived from one
   denial is a real liability, not a theoretical one.

The group counter-text carries the attribution (`outcome as the Board recorded it`), which is why
there is no footer paragraph saying it.

## Part B — the server roll-up

New file `server/professionalRecord.ts`. It reads sources that already exist and emits one shape.

```ts
export type ProfessionKey = "contractors" | "design" | "expediters" | "zoningAttorneys"
  | "taxAttorneys" | "lenders";

export interface ProfessionalEntry {
  /** Display name, in the spelling of the most recent record. */
  name: string;
  /** Normalized key used for grouping. Never shown. */
  key: string;
  /** "General Contractor", "Self-Certified Architect", "Zoning attorney", … */
  role: string;
  /** Firm, when a source carries one separately from the name. */
  firm?: string;
  /** ISO date of the most recent record here. Drives the sort and the right rail. */
  lastSeen: string;
  /** Granularity of lastSeen — tax appeals are year-only. */
  lastSeenPrecision: "day" | "month" | "year";
  recordCount: number;
  /** Up to two short facts. More than two is a design error, not a data question. */
  facts: string[];
  /** Outcome of the matter, in the deciding body's words. Never a rate. */
  outcome?: string;
  /** Only "ARDC verified" today. */
  tag?: string;
  /** Lenders only. */
  position?: "Current" | "Prior";
  /** Discovery deep link, or undefined when the firm is not in that index. */
  discoveryUrl?: string;
}

export interface ProfessionalRecord {
  groups: Array<{ key: ProfessionKey; label: string; note?: string; entries: ProfessionalEntry[] }>;
  totalNames: number;
  groupCount: number;
  firstYear: number | null;
  lastYear: number | null;
  sourceCoverage: Record<string, { status: "available" | "partial" | "unavailable" }>;
}
```

### Name normalization — this is the whole build

The same firm will arrive as `NORCON INC`, `NORCON, INC.` and `NORCON`. A roll-up that does not
dedupe will look broken on first glance, and nothing else in the section matters if this fails.

`zba/index.ts:12` already has the normalizer. **Move it to `shared/` and use it everywhere** rather
than writing a second one:

```ts
export function normalizeProName(raw: string | null): string {
  if (!raw) return "";
  return raw
    .toUpperCase()
    .replace(/,?\s*(ESQ\.?|ATTORNEY|ATTY\.?|JR\.?|SR\.?|III|II|IV)/gi, "")
    .replace(/,?\s*\b(INC|LLC|LLP|LTD|CO|CORP|COMPANY|PC|PLLC)\b\.?/gi, "")
    .replace(/[^\w\s]/g, " ")
    .replace(/\s+/g, " ")
    .trim();
}
```

The entity-suffix clause is new — `zba/index.ts` strips honorifics because it was written for
people, and §25 groups firms too. Update `zba/index.ts` to import the shared one so the two never
diverge. Group on the normalized key; **display the spelling from the most recent record**, which
is the one most likely to still be current.

`lienSearch.ts:92` has a third normalizer, `lenderNamesMatch`. Leave it alone for now — it does
fuzzy *matching* between two names, not canonicalization, and changing it would touch
release-reconciliation logic that is not in this step's blast radius.

## Part F — three contact-slot bugs, and why v1 has no citywide counts

The design calls for a citywide permit count beside each name — not as a ranking, but as a
reachability signal: a GC with 212 permits can be called, a GC with one is probably gone. **It is
not in v1,** because all three of these are true today:

1. **`permits.ts:291` loops `for (let i = 1; i <= 3; i++)`** while `chicagoPermits.ts:21–28`
   declares `contact_1` through `contact_4`. **The fourth contact is dropped on every permit.** On
   a permit carrying owner, GC, architect and expediter, one of them is silently lost.
2. **Discovery's rankings read `contact_1_*` only.** `architectRankings.ts:280` filters
   `contact_1_type in (...)` and groups on `contact_1_name`. Discovery sees the first slot and
   nothing else, so a firm that filed in slot 2 is absent from the citywide index however large it
   is.
3. **Discovery is scoped to `FIVE_YEARS_AGO`.** Anything before roughly 2021 will never match.

Together these mean a §25 row would say *"not in the citywide index"* about an active firm with
hundreds of permits — which makes the whole page look wrong and is the section's worst failure
mode. Fix the slots in their own step, then add the counts.

**Fix 1 is a one-character change and should go in this step** (`i <= 3` → `i <= 4`), because §25
is what makes the loss visible. Fixes 2 and 3 are Discovery changes with their own blast radius.

### Also broken, and in scope for whoever touches tax appeals next

`server/data/build_tax_appeal_attorneys.mjs:48–49`:

```js
    totalAppeals: a.wins, // approximation — we have wins count only
    winRate: 0,           // omitted since we don't have total appeals
```

The builder queries `result='Decrease'` only and never fetches the denominator, so
`wins === totalAppeals` by construction and `winRate` is hardcoded to zero. Anything rendering
those fields shows either 0% or a fabricated 100%. Separately, `wins` counts PIN-year rows, not
matters — one appeal covering 300 parcels counts 300 times.

**No citywide attorney success rate can be shown until this is fixed.** §25's `2 of 3 decreased`
is computed from the raw `7pny-nedm` rows for this PIN, not from this rollup, which is why it is
safe.
