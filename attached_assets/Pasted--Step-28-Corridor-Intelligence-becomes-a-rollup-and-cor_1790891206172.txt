## 3. Records stay listed — but one line each

**Corridor lists everything on the corridor.** Someone opening this section wants the whole corridor
picture without leaving it; a count that sends them elsewhere does not answer that. The two-column
layout (businesses on the left, construction on the right) is kept.

**What stops repeating is the per-record detail**, which belongs to the section that owns the record:
architect, GC, reported cost, city class, parking, case numbers, applicant, proposal text. Those
are why this section was ~800 lines. Each corridor row carries **name or address · one meta line ·
date**, and links to its full record.

| Column / block | Row shows | Row links to |
|---|---|---|
| Businesses with new licenses | business name · address · **every license category as a `.kyp-liccat` chip** · license start | `#section-new-business-licenses` |
| New construction | address · use · **units · stories · parking · reported cost · distance** · issue date · **architect and GC, each linked into Discovery** | `#development-permits` |
| Zoning activity | address · type · zone · decision · month | `#development-zba` |
| DPD applications | address · application type · status · month | `#development-proposed` |
| Corridor coverage | the standard news row — see §6d | the article |

Each column header carries an `all {n} →` link to the same anchor, so the full-detail view is one
click away. Those anchors already exist — Step 27 created `development-permits`,
`development-proposed`, `development-zba`, `development-news` (`RunDetail.tsx:3469`, `:3494`).

**Rewrite** `CorridorIntelligenceView.tsx` `220–258` (licenses + construction grid), `273–288`
(zoning) and `289–306` (DPD applications) to the `.kyp-corrrow` markup in the target.

**No new server fields.** `CorridorCardData` already carries everything these rows need:
`CorrLicense.tags` (the license categories), and `CorrConstruction.{use, stories, units, parking,
cost, distanceMi, architect, gc, cityClass}`. The architect and GC are already on the card and
already rendered today at `:250` — they just become Discovery links, the same `.kyp-pro` markup
Step 27 added to §development .1.

> ### ⚠ The row is a `<div>`, not an `<a>`
>
> A row has several destinations: the record itself, the architect, the GC. Wrapping the whole row
> in an anchor nests `<a>` inside `<a>`, which is invalid — the browser auto-closes the outer one and
> every link and style after that point silently breaks. **Link the name or address only.** This is
> not hypothetical; the first draft of this target did it and the architect link rendered as
> unstyled 17px body text.

**Keep `260–271`, the coverage rows — but render them as news, not as a bespoke row.** News is the
one record type this section owns; it is already deduped against §News by `withoutRepeatedNews`
(`RunDetail.tsx:3058`). Replace `.covtitle` / `.covmeta` / `.covsum` with **`NewsArchCard`** — see
§6d. Every news surface in the report uses the same row.

Since the cards no longer render record detail, `CorridorCardData` drops `licenses`,
`construction`, `zoning` and `dpdApplications` as arrays and gains four counts. **Compute the counts
server-side from the corridor field** — see §5 — rather than rebuilding the maps client-side.

## 3a. Each corridor is an UNNUMBERED subhead

Every corridor gets its own `KypSubhead` inside a `.subwrap` — the same pattern §21 Schools uses for
Elementary / High Schools and §25.5 Places of Worship uses for each religion group.

```jsx
{sorted.map((c, i) => (
  <div className="subwrap" key={c.key}>
    <KypSubhead className={i === 0 ? "first" : undefined}>
      <span className="lbl">{c.name}</span>
      <span className="ct">Tier {c.tier} · {c.tierLabel} · {c.onCorridor ? "on corridor" : `${c.distanceMi} mi`}</span>
    </KypSubhead>
    …
  </div>
))}
```

**Pass no `subsection`.** Numbered subsections are a fixed table of contents — §development always
has four, §25 always has five. The corridor count varies by property: one address has three
corridors, the next has one. Numbering instances rather than topics would give you `22.1–22.3` on
one report and `22.1` on the next, for the same section.

This also deletes four bespoke rules from the patch — `.kyp-corrcard`, `.kyp-corrhead`,
`.kyp-corrtier`, `.kyp-corrdist` — because `.subwrap` and `KypSubhead` already do that work.

**`first` on the first corridor only.** `.kyp-subhead` carries `border-top`, so the first one sitting
directly under the rollup blocks would otherwise draw a rule against them.

## 5. Server — one resolver, used everywhere

Step 27 added the corridor resolver in `server/developmentPipeline.ts` (reads `CORRIDOR_KEYWORDS`
at `:269`). This step **extends its use and deletes the client-side duplicate.**

### 5a. Delete the inline matcher

`RunDetail.tsx` builds corridor regexes **twice** — once for the collapsed-header badges
(`~16609–16719`) and again for the card payloads (`~16738–16829`) — with separately constructed,
identical patterns:

```js
name.toLowerCase().split(/\s+/) → drop ['avenue','ave','street','st','boulevard','blvd']
new RegExp(`\\b${base}\\s+(ave|avenue|st|street|blvd|boulevard)`, 'i')
```

**It matches the address string only, with no coordinate check.** A business license at
7000 W Chicago Ave therefore matches the West Town "Chicago Avenue" corridor, whose box is
`lat 41.894–41.90, lng -87.70 to -87.64`. Delete both copies and use the server field.

### 5b. Two bugs this removes

1. **ZBA badge and list disagree.** At `~16700` the badge count skips the distance test when the
   property has no geocode; at `~16817` the list computes distance `99` in the same situation, which
   fails `> 1.0` and **drops every ZBA case**. Header says 4, list shows 0.
2. **Double matching.** Each record type is matched twice per render.

### 5c. Add `corridor` to the two remaining sources

Permits, DPD applications and ZBA cases already carry it from Step 27. Add the same
`corridor: { key, name, tier } | null` field, from the same resolver, to:

- **business licenses** — `/api/new-business-licenses` (or whichever route feeds
  `nearbyLicensesData`)
- **news articles** — alongside the existing `corridorKeys`, so one shape is used everywhere.
  `corridorKeys` can stay as the server's internal multi-match; the client reads `corridor`.

Same rule as Step 27: **name match AND inside the bbox** (or within ~120 m of `line` for the three
diagonal corridors). Name alone is what produces the 7000 W Chicago Ave bug above.

### 5d. Return corridor counts

The corridor payload returns, per corridor: `licenses`, `permits`, `zoningAppeals`,
`dpdApplications`, `articles` as counts, deduped the way the current KPI totals already dedupe
(`permitNumber`, `licenseEstablishmentKey`, `url`, `caseNumber` — `RunDetail.tsx:16856–16878`).
Move that dedup server-side with the matching; do not leave it split across both.
