## LOGIC (front-end / binding rules)

### 1. Mix bars
- One row per **distinct license-mix combination** present in the data (e.g. `{Retail Food}`, `{Retail Food, Liquor/Tavern}`, `{Retail Food, Liquor/Tavern, Entertainment}`, `{Liquor/Tavern}`, …). Sort rows by business count **descending**.
- Bar width `{PCT}` = `count / maxBucketCount * 100`. Fill is `<i>` `display:block`, indigo — never inline `<span>`.
- Counts across all mix rows **must sum to `{TOTAL_BUSINESSES}`** (each business is in exactly one mix bucket). This is the integrity check.
- Tag order inside a row: put the "lead" type first with `.mixtag.lead` (Food if the mix contains food; else the primary type). Keeps the eye on the dominant use.

### 2. Click-to-filter
- Clicking a `.mixrow` filters the business list below to that exact mix bucket; add `.active` to the clicked row, filter the `.biz` list to `business.mix_key === bucketKey`, and update the divider label to `{N} businesses · {mix label}`. Clicking the active row again clears the filter (back to all, nearest first).
- **Filter model = exact combination** (clicking "Retail Food + Liquor/Tavern" shows only those, not all liquor holders). If instead you want a type-level filter ("show all liquor holders across any combo"), that's a different model — pick ONE and keep the hint copy honest ("click a row to filter"). Default: exact combination.

### 3. Takeaway copy is DERIVED from the mix (compute, don't free-form)
Compute these from the buckets and fill the sentence templates:
- `food_involved` = businesses whose mix contains Retail Food. `liquor_involved` = mix contains Liquor/Tavern. `standalone_bars` = mix is exactly `{Liquor/Tavern}`. `food_only` = mix is exactly `{Retail Food}`.
- **Bullet 1 (the important one):** state `food_involved` of `total`, then `food_only`, then "plus {food_involved − food_only} that pair food with liquor or entertainment," then **`standalone_bars` standalone bars.** The conclusion ("dining scene with a nightlife layer, not a bar district") is only valid when `standalone_bars` is small relative to `food_involved` — if standalone bars are actually a large share, flip the framing to match the data. Never hardcode "not a bar district."
- **Bullet 2:** the three **nearest** businesses with their distances.
- **Bullet 3 (dedup note):** "{TOTAL_LICENSES} licenses grouped by establishment → {TOTAL_BUSINESSES} real openings." Show ONLY when `TOTAL_LICENSES > TOTAL_BUSINESSES` (something was actually merged); otherwise omit it.

### 4. Business list
- Sorted by `distance_mi` ascending (nearest first). Cap the initial render (e.g. 6); "Show all {TOTAL_BUSINESSES} within 1 mile →" reveals the rest.
- `license_type` values: display each DISTINCT type the business holds, `·`-separated, in indigo (`.lic`). Append the amber `.n2` "{N} licenses" tag **only when `license_count > 1`** — this is the visible proof of the dedup. **The tag is amber (`--cautionText`/`#fdf3df`), never red** — holding several licenses isn't bad, it's just informative.
- `{ISSUE_MONTH_YEAR}` = the business's earliest in-window issue date, formatted "Mon YYYY" (not ISO). If license issue dates differ across the business's licenses, you may show per-license dates in parentheses (see Deliz row in the reference).

### 5. Source line
Fixed methodology copy: new issuances only / excludes renewals / past 12 months / **grouped by establishment** (state the exact key you used — name+address or account+site) / count-once note / covered license categories. Match the dedup key you actually implemented.
