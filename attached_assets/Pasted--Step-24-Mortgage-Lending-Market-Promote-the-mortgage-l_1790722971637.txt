## 1. The problem, stated once

The mortgage surface is split across two parents and buried two levels deep.

```
16  PRE-TITLE CHECK                         ← accordion row, id "debt"
    └─ <PreTitleCheck>  "Can I Finance This Property?"   ← collapsible #1
        └─ children:
            ├─ Area Transaction Trends       ← collapsible #2   (broken)
            ├─ Local Mortgage Market Activity ← collapsible #2
            └─ Commercial Lending Activity    ← collapsible #2

22  NEIGHBOURHOOD & PEOPLE                  ← accordion row, id "people"
    ├─ Who's Buying Right Now?              ← HMDA, filed under demographics
    └─ Recently Sold Comps                  ← comps, filed under demographics
```

The three under Pre-Title Check are passed as the `children` prop and render **inside** the
Pre-Title Check collapsible (`PreTitleCheck.tsx:626–630`), so the user must open a title-risk check
before they can reach the mortgage market.

**The registry already declares the fix and nobody built it.**
`client/src/components/report/sectionRegistry.tsx:36`:

```js
market: { id: "market", anchorId: "print-section-comparable-sales", title: "The Local Market",
  summary: "Comps, price trends and mortgage-lending activity nearby.",
  info: ["Recently sold comps", "Area transaction trends", "HMDA — who's borrowing",
         "HMDA — what's getting funded", "Commercial lending (SBA)"] }
```

`market` is in `SECTION_ORDER` (:7) and `scanBuilder.tsx:121` populates `dyn.market` — but `market`
is **absent from `ACC_DEFAULT_ORDER`** (`RunDetail.tsx:1270`). It exists as a scan card that jumps
into the middle of §People. This step finally builds the row it points at, renamed
**Mortgage & Lending Market**.

```jsx

Stop passing children and that block never renders. **Zero edits to `PreTitleCheck.tsx`.** This is
deliberate: it makes the step safe against whatever owner-lien work exists in Replit but not in

## 8. Prompt 5 — Area Transaction Trends: the data fix

**Separate prompt, server only, no UI change.** Run it after 1–4 so a data-layer bug never rides
along with a 1,400-line JSX move.

### 8.1 Diagnosis

The panel is **not** showing "no data for this ZIP." `getTransactionTrends` builds
`years` as `TARGET_YEARS.map(...)` — always four entries, even when every count is zero. The client
renders its fallback only when `transactionTrendsData?.years?.length > 0` is falsy, which requires a
**non-OK HTTP response**. The route returns:

- `400` — only for a malformed ZIP, and the client applies the same `/^\d{5}$/` guard, so unreachable
- `503` — when `getTransactionTrends` returns `null`
- `500` — on a throw, but `getNbhdsForZip` and `buildSaleHistCache` both catch internally

`null` is returned at exactly one line: `if (!saleHistCache) return null`. **So
`buildSaleHistCache()` is failing.** It swallows the error into:

```
[TransactionTrends] Sale history cache failed: <message>
```

**That line is in the Replit console right now and names the cause.** Read it before changing
anything.

The likely cause is the query itself. It fetches **every Chicago sale since 2022**, grouped by
year × nbhd × class, `$limit=200000`, on a 30-second `AbortSignal.timeout` — to answer a question
about one ZIP. React Query retries 3×, so the empty state appears ~90 s after load.

### 8.2 The second bug, which the first one is hiding

The neighbourhood join key is built two different ways:

```ts
// getNbhdsForZip — reads nbhd from the ASSESSOR UNIVERSE (c49d-89sn), then pads and prefixes
const nbhdPadded  = String(row.nbhd || '').padStart(3, '0');
const saleHistNbhd = tc + nbhdPadded;          // e.g. "74" + "011" = "74011"

// buildSaleHistCache — reads nbhd from PARCEL SALES (wvhk-k5uv) and uses it RAW
const nbhd = String(row.nbhd || '');
```

Both are Cook County Assessor datasets and almost certainly use the same convention. If they do,
one side is wrong and **every ZIP matches zero neighbourhoods**. Fix the fetch alone and the panel
renders four zero-height bars instead of an error — which looks like working code. **Both must be
fixed together.** Confirm the convention with one probe before writing the fix:

```
https://datacatalog.cookcountyil.gov/resource/wvhk-k5uv.json?$select=nbhd,township_code&$limit=3
https://datacatalog.cookcountyil.gov/resource/c49d-89sn.json?$select=nbhd,township_name&$limit=3
```

If `wvhk-k5uv.nbhd` is already 5 digits, drop the `tc +` concatenation. If it is 3 digits, apply the
same `township_code + pad(nbhd,3)` on **both** sides.

### 8.3 Third bug

`getNbhdsForZip` uses `$limit=500` with **no `$group`** against a ZIP holding tens of thousands of
parcels, so it samples 500 arbitrary rows and can miss neighbourhoods. Add
`$group=township_name,nbhd` (or `$select=distinct township_name,nbhd`) and drop the limit to
something small.

### 8.4 The prompt

> In `server/transactionTrends.ts`:
>
> 1. First read the Replit console for `[TransactionTrends] Sale history cache failed:` and report
>    the message before changing code.
> 2. Probe both Socrata datasets for the real shape of `nbhd` (the two URLs above) and report what
>    you find. Do not guess.
> 3. **Scope the sale-history query to the ZIP's neighbourhoods instead of the whole city.** Resolve
>    `getNbhdsForZip(zip)` first, then fetch sales filtered to `nbhd in (…)` for that ZIP only.
>    Delete the global `saleHistCache` / `saleHistPromise` machinery and cache per ZIP with the
>    existing 7-day TTL. This is the fix for both the timeout and the wasted work.

## 10. Prompt 6 — Recently Sold Comps: stop stating something false

**Client + a small server addition. No data-source change** — replacing the characteristics file is
a separate step (§11).

### 10.1 The one false statement in the section

`ComparableSalesView.tsx` renders, when no comps survive:

```jsx
`No sales found within ${searchParams.radiusMiles} mi for class ${searchParams.propertyClass} in the last ${searchParams.monthsBack} months.`
```

For a commercial subject that sentence is **factually wrong**. Trace it:

| Step | What happens | Line |
|---|---|---|
| 1 | `wvhk-k5uv` returns sales for the class — often 100+ rows | `comparableSales.ts:97` |
| 2 | Count is logged and then discarded | `:107` |
| 3 | Characteristics fetched from `bcnq-qi2z` | `:119` |
| 4 | `if (!c) continue;` drops every sale with no characteristics row | `:136` |
| 5 | `candidates` empty → radius expands 0.75 → 3.0 mi finding nothing | `:163–195` |
| 6 | `totalCandidates: joined.length` — counted **after** the join, so `0` | `:235` |

`bcnq-qi2z` is titled *"Assessor **[Archived 05-11-2022]** — Residential Property Characteristics"*
and the selected fields are `beds`, `fbath`, `hbath` — residential-only concepts. So for commercial
classes the join almost certainly returns nothing and all the sales die at step 4.

**A genuinely empty area and a total join failure produce byte-identical responses.** The number
that tells them apart is computed at step 2 and thrown away.

### 10.2 What is NOT wrong — do not remove anything

The comps themselves are sound and already disclosed honestly. `ComparableSalesView` renders a
confidence pill, the comp count, `{radius} mi radius · last {months} months · {n} total nearby
sales`, an expanded-radius warning above 0.75 mi, and *"Same property class required for matching.
Informational only — not a certified appraisal."* Sale prices, dates, distances and class matches
are all real county records. **Keep the section. Keep the comp cards. Keep the medians.**
